# make-docs

## 目的

プロジェクトの大元要件（`/requirements` → `/more-requirements` → `/detail`の最初の1回だけのルート）が完了した後、新機能追加・修正・改善のたびに使用する日常的な入口。

要望を実装着手可能な粒度まで整理し、必要な場合のみ技術設計（DB・API・画面挙動・構成・意思決定）も同じドキュメントに含める。承認後、種別に応じた保存先へ1件作成または更新する。

Issue起票、コード実装は行わない。

## 使用方法

```text
/make-docs お問い合わせフォームにファイル添付を追加したい
/make-docs docs/maintenance/contact-attachment.md
```

## 手順

1. 引数を確認する。
   - 新規要望の概要の場合：関連する既存ドキュメント（`docs/requirements/`、`docs/maintenance/`、`docs/design/`）と既存コードを確認する。
   - 既存ファイルのパスの場合：そのドキュメントを読む。
2. 新機能か修正・改善かデザイン・基盤方針かを判別する。曖昧な場合は人間に確認する。
3. 要望を一度に2〜3問ずつヒアリングする（観点は下記）。
4. 技術設計の深掘りが必要な変更（DB・API・画面挙動・構成・技術選定に影響するもの）は、該当する範囲だけ追加でヒアリングする。不要な変更では技術設計の質問をしない。
5. 要件案（技術設計を含む場合はその内容も）を提示する。
6. GOサイン後、種別に応じた保存先へドキュメントを作成または更新する。
7. 結果と次の工程を報告する。

質問は次の観点で、実装着手可能な粒度まで詰める。

- 目的・背景、利用者（新規作成の場合）
- 必要な挙動：正常系だけでなく、分岐・エッジケース・例外時の挙動
- 受け入れ条件：前提・操作・期待結果が判定可能な文章になっているか
- 対象外：曖昧な境界がないか
- 制約：技術・運用・期限などの制約が具体化されているか
- 技術設計（該当する場合のみ）：DB変更、API変更、画面・状態遷移、構成/技術選定、意思決定事項
- 未決事項：優先して解消する。解消できない場合は理由とともに残す

既存情報を再質問せず、不明点を推測で補わない。曖昧な回答には短い例や選択肢を提示する。

## 種別と保存先

| 種別               | 保存先                |
| ------------------ | --------------------- |
| 新機能             | `docs/requirements/`  |
| 修正・改善         | `docs/maintenance/`   |
| デザイン・基盤方針 | `docs/design/`        |

「デザイン・基盤方針」は、特定の新機能や個別の修正ではなく、デザインシステム・トンマナ刷新など複数画面・複数機能にまたがる恒久的な方針を指す。個別画面の文言修正や単発のUI調整は「修正・改善」として扱う。

## ドキュメント構成

```markdown
# 要件名

## 目的・背景

## 利用者

## 必要な挙動

## 受け入れ条件

## 対象外

## 制約

## 技術設計（該当する場合のみ）

## 未決事項
```

`技術設計`セクションは、該当する内容がない場合は省略する。無理に埋めない。

## 承認後

GOサインを得た場合のみ、次の手順でドキュメントを作成または更新する。

1. 現在のブランチと作業ツリーを確認する。

   ```bash
   git branch --show-current
   git status --short
   ```

   `main`・`develop`以外の作業ブランチ（Issue用ブランチ等）に既にいる場合は、新規ブランチを作成せずそのブランチ上で作業する。

2. `main`または`develop`にいる場合は、`develop`を最新化してドキュメント作成専用ブランチを作成する。

   ```bash
   git fetch origin
   git switch develop
   git pull --ff-only origin develop
   git switch -c "docs/<内容の kebab-case>"
   ```

3. 種別に応じた保存先へドキュメントを作成または更新する。
   - 新規作成：内容を表す短いkebab-caseのファイル名で作成する
   - 既存更新：ファイル名・保存先は変更しない

4. 作成・更新したファイルだけをステージし、日本語メッセージでコミットする。

   ```bash
   git add -- '<ファイルパス>'
   git commit -m 'docs: <日本語の変更内容>'
   ```

5. 手順2で新規にdocsブランチを作成した場合は、Pushして`develop`向けのPull Requestを作成する。

   ```bash
   git push -u origin "docs/<内容の kebab-case>"
   gh pr create --base develop --head "docs/<内容の kebab-case>" \
     --title "docs: <日本語のタイトル>" --body-file -
   ```

   Draft PRは使用しない。既存の作業ブランチ上で行った場合はPRを作成しない。

## 禁止事項

- 承認前のドキュメント作成・更新
- Issue起票、ドキュメント以外のコード変更
- `main`・`develop`への直接コミット
- 要件にない機能の追加や仕様の推測
- 不要なクラス・レイヤー・パターンの提案
- 複数ドキュメントの同時作成
- 既存PRの上書き、Draft PRの作成、PRの自動マージ

`Write`は承認後の新規作成、`Edit`は承認後の既存ドキュメント更新だけに使用する。`Bash`はGit操作・PR作成と情報確認に使用する。

## 完了報告

- 種別（新機能／修正・改善／デザイン・基盤方針）
- 作成または更新したファイル
- 使用したブランチ名（新規docsブランチの場合はPR番号・URLも）
- 要件・技術設計の概要
- 残った未決事項
- 次の工程

次は `/issue <ドキュメントのパス>` でIssueへの分割と起票を進める。docsブランチ上で作業した場合は、PRが`develop`へマージされた後に実行すること。
