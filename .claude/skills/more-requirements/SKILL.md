# more-requirements

## 目的

`/requirements`で作成した大枠の要件ドキュメントを入力に、実装着手に十分な詳細度まで要件を深掘りする。

プロジェクト全体の大元要件を定義する最初の1回だけのルート（`/requirements` → `/more-requirements` → `/detail`）で使用する。個別の新機能・修正・改善は`/make-docs`を起点とする。

新規ドキュメントの作成、技術設計、Issue起票、コード調査、実装は行わない。

## 使用方法

```text
/more-requirements docs/requirements/contact-form.md
```

## 手順

1. 指定された要件ドキュメントを読む。
2. 関連する既存ドキュメント・既存コードを確認し、記載内容との矛盾がないか確認する。
3. 各項目を1つずつ批判的にレビューし、曖昧・未決・実装判断不能な箇所を弱点として洗い出す。加えて、後述の「必須確認チェックリスト」の各観点についても要件ドキュメントに記載があるか確認し、記載がなければ弱点に追加する（ユーザーの回答内容に含まれていない観点でも、必ず自発的に洗い出す）。洗い出した弱点を質問の前に提示する。
4. 弱点1件につき1問ずつ質問する。複数の論点をまとめて質問しない。
5. 回答が曖昧な場合（後述のNG例に該当する場合を含む）は、具体例・数値・選択肢を示して同じ観点を再質問する。判定可能な粒度になるまで次の弱点へ進まない。
6. すべての弱点を解消したら、深掘りした要件案を提示する。
7. GOサイン後、対象の要件ドキュメントを更新する。新規ファイルは作成しない。
8. 更新結果と次の工程を報告する。

質問は次の観点で、`/requirements`より一段深い粒度まで詰める。

- 必要な挙動：正常系だけでなく、分岐・エッジケース・例外時の挙動
- 受け入れ条件：前提・操作・期待結果が判定可能な文章になっているか
- 対象外：曖昧な境界がないか
- 制約：技術・運用・期限などの制約が具体化されているか

既存情報を再質問せず、不明点を推測で補わない。曖昧な回答には短い例や選択肢を提示する。

### 曖昧な回答として再質問する例

次のような、判定基準を含まない表現は曖昧な回答として扱い、具体化するまで通過させない。

- 「適切に」「よしなに」「普通に」「なるべく」「基本的に」「必要に応じて」
- 数値・上限・タイムアウトなどを伴わない「大量」「高速」「すぐに」
- 誰が読んでも同じ判定になるか不明な「わかりやすく」「使いやすく」

### 受け入れ条件の粒度チェック

受け入れ条件は、次をすべて満たすまで書き直しを求める。満たさないまま承認済みとして通過させない。

- 前提・操作・期待結果の3点が文章に含まれている
- 第三者が読んでも同じ合否判定になる
- 上記の曖昧語を含まない
- 数値・状態・エラーメッセージなど判定可能な具体値がある場合は明記している

### 必須確認チェックリスト

ユーザーの回答や要件ドキュメントの記載に登場していなくても、次の観点は毎回レビューし、記載がなければ弱点として扱う。該当しない場合は「対象外」として理由とともに明記する。ユーザーからの言及を待つ受け身の姿勢ではなく、レビュー段階で自発的に洗い出す。

- 画面・UI構成：主要画面の一覧と遷移（一覧→詳細など）
- 初期状態：データが1件もない場合の表示・挙動
- 異常系：保存・通信・入力などが失敗した場合の挙動
- 対応環境：対応プラットフォーム・対応言語・対応ブラウザ/デバイス
- 境界値：件数・文字数・金額などの上限/下限に達した場合の挙動
- 同時実行・競合：同じデータへ複数の操作が重なった場合の挙動
- 権限：利用者によって操作可否が変わるか

## 対象ドキュメント構成

`/requirements`と同じ構成を維持し、内容の深さだけを更新する。項目自体は追加・削除しない。

```markdown
# 要件名

## 目的・背景

## 利用者

## 必要な挙動

## 受け入れ条件

## 対象外

## 制約

## 未決事項
```

`未決事項`は、解消できた項目から本文へ反映する。解消できない場合は理由とともに残す。

## 承認後

GOサインを得た場合のみ、指定された要件ドキュメントを更新する。

ファイル名・保存先は変更しない。新規ドキュメントは作成しない。

## 禁止事項

- 承認前のドキュメント更新
- 新規ドキュメントの作成
- 技術設計、コード変更、Issue起票
- 要件にない機能の追加や仕様の推測
- 指定外のドキュメントの変更

`Edit`は承認後の対象ドキュメント更新だけに使用する。`Bash`は情報確認だけに使用する。

## 完了報告

- 更新したファイル
- 洗い出した弱点と解消状況
- 詳細化した内容の概要
- 残った未決事項
- 次の工程

次は、技術設計が必要な場合は`/detail`、不要な場合は`/issue <要件ドキュメントのパス>`でIssueへの分割と起票を進める。
