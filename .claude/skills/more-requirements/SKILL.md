# more-requirements

## 目的

`/requirements`で作成した大枠の要件ドキュメントを入力に、実装着手に十分な詳細度まで要件を深掘りする。

プロジェクト全体の大元要件を定義する最初の1回だけのルート（`/requirements` → `/more-requirements` → `/detail`）で使用する。個別の新機能・修正・改善は`/plan-docs`を起点とする。

新規ドキュメントの作成、技術設計、Issue起票、コード調査、実装は行わない。

## 使用方法

```text
/more-requirements docs/requirements/contact-form.md
```

## 手順

1. 指定された要件ドキュメントを読む。
2. 関連する既存ドキュメント・既存コードを確認し、記載内容との矛盾がないか確認する。
3. 各項目を深掘りするための質問を一度に2〜3問ずつ行う。未決事項があれば優先して解消する。
4. 深掘りした要件案を提示する。
5. GOサイン後、対象の要件ドキュメントを更新する。新規ファイルは作成しない。
6. 更新結果と次の工程を報告する。

質問は次の観点で、`/requirements`より一段深い粒度まで詰める。

- 必要な挙動：正常系だけでなく、分岐・エッジケース・例外時の挙動
- 受け入れ条件：前提・操作・期待結果が判定可能な文章になっているか
- 対象外：曖昧な境界がないか
- 制約：技術・運用・期限などの制約が具体化されているか

既存情報を再質問せず、不明点を推測で補わない。曖昧な回答には短い例や選択肢を提示する。

## 対象ドキュメント構成

`/requirements`と同じ構成を維持し、内容の深さだけを更新する。項目自体は追加・削除しない。

```markdown
# 要件名

## 目的・背景

## 利用者

## 必要な挙動

## 受け入れ条件

## 対象外

## 制約

## 未決事項
```

`未決事項`は、解消できた項目から本文へ反映する。解消できない場合は理由とともに残す。

## 承認後

GOサインを得た場合のみ、指定された要件ドキュメントを更新する。

ファイル名・保存先は変更しない。新規ドキュメントは作成しない。

## 禁止事項

- 承認前のドキュメント更新
- 新規ドキュメントの作成
- 技術設計、コード変更、Issue起票
- 要件にない機能の追加や仕様の推測
- 指定外のドキュメントの変更

`Edit`は承認後の対象ドキュメント更新だけに使用する。`Bash`は情報確認だけに使用する。

## 完了報告

- 更新したファイル
- 詳細化した内容の概要
- 残った未決事項
- 次の工程

次は、技術設計が必要な場合は`/detail`、不要な場合は`/issue <要件ドキュメントのパス>`でIssueへの分割と起票を進める。
