# 🎫 issue — GitHub Issue 作成

要件ドキュメントを最小限の縦割りIssueへ分割し、承認後にGitHub Issueを起票するスキル。

## 使い方

```
/issue docs/requirements/contact-form.md
/issue docs/maintenance/contact-attachment.md
```

## パイプライン

```
前提: 要件ドキュメントが存在すること（通常は/plan-docsが作成したもの）
読込: 指定された要件ドキュメント / 既存Issue（重複確認）
出力: GitHub Issue
次:   /analyze <Issue番号>
```

## 分割方針

- 1画面（1機能ページ）につき1Issueを基本単位とする。操作（一覧表示・作成・更新・削除など）ごとの過剰な細分化はしない
- Issue数は最小限にする（1件で安全に完結する内容を分割しない）
- 技術レイヤー単位（Controller/Request/Bladeなど）で横分割しない
- 「単独でマージされたとき、確認できる完了状態を持つか」を基準にした縦割りの機能単位（画面単位）で分割する
- 画面単位から分割するのは、独立した技術基盤(chore)・別ユーザー向け機能の混在・先行部分だけで独立して価値を確認できる依存関係がある場合に限る
- 要件ドキュメントの「対象外」「制約」を関係するIssueへ転記する

## プロセス

1. 要件ドキュメントを読む。未決事項があれば推測でIssue化せず人間へ確認する
2. 既存Issueとの重複を確認する
3. Issue案（目的・受け入れ条件・対象外・制約・依存関係・関連要件）を提示 → 承認
4. `gh label list`でラベルの存在を確認し、承認されたラベルを指定して起票
5. 依存関係がある場合は前提Issueを先に起票し、確定した番号を後続Issueへ埋め込む

## ルール

- 承認なしにIssueを作成しない
- 存在しないラベルを指定しない。新規ラベル作成は人間の承認後のみ
- 受け入れ条件は「前提・操作・期待結果」が判定できる文章にする
- 起票に1件でも失敗したら後続の起票を停止し、状況を報告する
